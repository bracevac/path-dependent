\section{Introduction}\label{sec:intro}
\mathplain

Scala 3 can check at compile time which capabilities a value may use \cite{scala3cc,boruchgruszecki2023capturing}. A capability is a value that gives access to an effect, such as a file handle or a logger. The checker writes capabilities into types, and it rejects a program whose types do not account for the capabilities it uses. This report explains why that verdict can be trusted, for capture checking over Dependent Object Types (DOT), by the route that \Rone took for type safety.

\paragraph{Capture checking.}
The chapter on capture checking in the Scala 3 reference \cite{scala3cc} opens with a method that lends a log file to an operation and closes the file when the operation returns. We quote the reference at commit \texttt{4dae25087d} throughout, by file and line. This is \texttt{basics.md}, lines 56 to 60:
\begin{lstlisting}[language=Scala]
def usingLogFile[T](op: FileOutputStream^ => T): T =
  val logFile = FileOutputStream("log")
  val result = op(logFile)
  logFile.close()
  result
\end{lstlisting}
The \lstinline|^| after the parameter type makes the file a capability whose uses the checker tracks. An operation that returns a closure over the file is rejected, with this message (lines 64 to 71):
\begin{lstlisting}[basicstyle=\ttfamily\footnotesize,columns=fixed,basewidth=0.52em]
   |  val later = usingLogFile { f => () => f.write(0) }
   |                           ^^^^^^^^^^^^^^^^^^^^^^^^^
   |  Found:    (f: java.io.FileOutputStream^'s1) ->'s2 () ->{f} Unit
   |  Required: java.io.FileOutputStream^ => () ->'s3 Unit
   |
   |  Note that capability f cannot be included in outer capture set 's3.
\end{lstlisting}
The closure \lstinline|() => f.write(0)| has the type \lstinline|() ->{f} Unit|, which says that it may use \lstinline|f|. Called after \lstinline|usingLogFile| has returned, it would write to a closed file. The expected result type has no room for \lstinline|f|, so the program is rejected before it runs. The verdict comes from types alone, so it can be trusted only if the types are right about runs: a value whose type lists a set of capabilities must use no others when the program runs. This report proves a statement of that kind for a calculus.

\paragraph{What is proved.}
The central theorem is effect safety, Theorem~\ref{thm:mini-effect} in the miniature and \lean{effect\_safety} in each of the three Lean trees described below. It speaks of a state $st$ of the machine of \FCdot, the store $\sigma$ of $st$, and a context $\Gamma$ that types that store. Let $\statej{st}{T}$ and $\storej{\sigma}{\Gamma}$. Let $\kappa$ be a capture variable with $\kappa \notin \leaves{\Gamma}{\uses{st}}$. Let $st \steps st'$, let $\storej{\sigma'}{\Gamma'}$ for the store $\sigma'$ of $st'$, and let $\insp{st'} = x$. Then $\kappa \notin \leaves{\Gamma'}{\cset{x}}$. In words: the use set $\uses{st}$ of a state is what the state may still use, computed from its syntax (Section~\ref{sec:cc-uses}). The leaves of a capture set are the capture variables it reaches when each variable in it is replaced by the capture set of its type (Section~\ref{sec:cc-types}). A state inspects the variable whose stored value its next step reads: the function of a call, the receiver of a projection, the box of an unboxing. So a run from a state whose use set does not reach $\kappa$ never calls, projects or unboxes a variable that reaches $\kappa$. The Lean has no names, and there the store of $st'$ extends that of $st$ along a renaming $\rho$ of locations, so the conclusion is about $\rho(\kappa)$. Effect safety is a corollary of capture prediction, which says that the leaves of the use set never grow along a run (Section~\ref{sec:mini-run}). For a DOT program over a platform of capabilities, Section~\ref{sec:source-thms} carries both through the translation, to a target state with the same erasure as the source state.

\paragraph{The route.}
Report~1 proved DOT type safe by a route that compilers take. A typing derivation is translated into a term of \FCdot, in which every use of subtyping is an explicit proof term, called evidence, that erases. Type safety of \FCdot rests on one theorem about closed evidence over a typed store (Section~\ref{R1-sec:idea} of report~1), and safety of DOT follows by running the source program and its translation side by side. This report adds capture sets to both calculi and keeps the route. Subcapturing becomes evidence too. Every binder declares the use set of its body and carries evidence that the body stays within it, so the use set of a term is computed from its syntax. One more theorem about closed evidence says that over a typed store, capture evidence relates only capture sets whose leaves are included (Theorem~\ref{thm:target-canon}). A use-set half of preservation then discharges, at each step, the evidence that the redex carries, so the leaves of the use set never grow. The source enters by translation. A DOT derivation becomes an \FCdot term together with evidence that its use set fits the declared one, and a source run is matched by a target run with the same erasure. The proof uses no logical relation.

\paragraph{Three trees.}
The development consists of three Lean trees. Each is a separate copy of the one before it, as its \texttt{BASE} file records. \treeK copies the vanilla tree of report~1 at commit \texttt{83079d4}, before pull request \#56, whose simplifications it does not follow. It models capture checking the DOT way: a capture parameter is a capture member of an object, and no typing rule reads a universal capability. \treeCC copies \treeK at \texttt{a4df821} and models the compiler's reading of the universal capability by scopes and levels. \treeCL copies \treeCC at \texttt{90fab2a} and adds capability classifiers. Report~1's conclusion lists five kinds of theorem that every copy of its development carries: canonical forms of closed evidence, preservation, progress, the erasure simulation, and the safety of the source by translation. Each capture tree has all five. Beyond them the trees differ, and Table~\ref{tab:matrix} says for each theorem the report cites which trees prove it.

\paragraph{What is mechanized.}
Every theorem stated in Sections~\ref{sec:target} to~\ref{sec:frontends} is a Lean declaration, and its head names the declaration and the tree. The miniature of Section~\ref{sec:mini} is a fragment of the \treeK target and is not mechanized on its own. Section~\ref{sec:mech-mini} maps each of its statements to the declaration it restricts. Every example is marked in one of three ways. It is decided when the kernel closes it by \lean{decide} or \lean{rfl}, or by running a checker whose soundness theorem turns the verdict into a derivation. It is built by hand when its Lean proof is written out. It is on paper when the Lean does not state it. The translation is defined by well-founded recursion and does not reduce in the kernel, so a translated example is a theorem about a derivation and not a computed term. The three trees contain no \lean{sorry}, no \lean{axiom} declaration and no \lean{native\_decide}, and the main theorems depend on propositional extensionality and quotient soundness only.

\paragraph{Reading paths.}
Section~\ref{sec:cc} introduces capture checking for a reader who has never seen it, and Section~\ref{sec:problem} shows why the textbook proof needs an inversion that capture members break. A reader of the Lean can start at Section~\ref{sec:mech}.

\paragraph{Conventions.}
As in report~1, source syntax and judgments are set in \src{blue}, target syntax and judgments in \tgt{red}, and the untyped runtime in black. Lean names are set in \lean{typewriter}. The Lean scopes syntax by de Bruijn indices, and the report names every binder instead. Rules are named in small caps with the judgment as a prefix, such as \rn{C-Var} for capture evidence and \rn{E-App} for a step. Report~1 named its target rules by their constructors instead. The trees are written out as \treeK, \treeCC and \treeCL.
