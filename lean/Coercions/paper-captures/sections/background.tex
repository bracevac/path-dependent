\section{Capture Checking for a Reader of Report~1}\label{sec:cc}
\mathplain

This section explains capture checking to a reader who knows System F and \Rone but has never seen a capture checker. It follows the Scala 3 reference \cite{scala3cc} and fixes the words that the rest of the report uses: capability, capturing type, subcapturing, leaf, use set and inspection. Section~\ref{sec:cc-closures} settles what the capture set of a closure bounds, which is where the report and Scala's documentation differ.

\subsection{Capabilities and capturing types}\label{sec:cc-types}

A capability is a value of interest, such as a file handle, an access token or a mutable data structure, and often it gives access to an effect (\texttt{overview.md}, line 48). In Scala source, a capability is a parameter, a local variable or the \lstinline|this| of a class whose type is a capturing type with a nonempty capture set (\texttt{basics.md}, lines 118 to 120). A capturing type $\capt{T}{\cset{c_1, \ldots, c_n}}$ stands for values of type $T$ that may use the capabilities $c_1$ to $c_n$. A type $T$ with no capture set, whose class does not extend \lstinline|Capability|, is pure and stands for $\capt{T}{\cempty}$ (\texttt{overview.md}, lines 78 to 80). Values of capturing types are capabilities too (line 84).

Function types carry capture sets in the same way (\texttt{basics.md}, lines 158 to 166). The arrow \lstinline|A -> B| is pure. The arrow \lstinline|A ->{c, d} B| abbreviates \lstinline|(A -> B)^{c, d}|, a function that may use $c$ and $d$ and nothing else. The impure arrow \lstinline|A => B| is \lstinline|A ->{any} B|. Here \lstinline|any| is the universal capability, from which every other capability is derived (line 123). It was written \lstinline|cap| until 2026 (documentation commit \texttt{77941adc59}). The reference also calls it the root capability (line 296), but report~1 already uses root for the variable under an atom's casts.

Capture sets are ordered by subcapturing. The reference writes $C_1 \mathrel{<:} C_2$ and reads it as ``$C_1$ is covered by $C_2$'' (line 269). Subtyping extends to capturing types: $\capt{T_1}{C_1} \mathrel{<:} \capt{T_2}{C_2}$ when $T_1 \mathrel{<:} T_2$ and $C_1 \mathrel{<:} C_2$ (lines 273 to 275). Subcapturing $C_1 \mathrel{<:} C_2$ holds when every element $c$ of $C_1$ meets one of three conditions (lines 277 to 281):
\begin{enumerate}
\item $c$ is an element of $C_2$,
\item $c$ refers to a parameter of a class \lstinline|Cls| and $C_2$ contains \lstinline|Cls.this|,
\item the type of $c$ has a capture set $C$ and $C \mathrel{<:} C_2$.
\end{enumerate}
The third case says that a capability is covered by the capture set of its type. It becomes rule \rn{C-Var} of Section~\ref{sec:mini-typing}, and it makes a capture set mean more than its elements. For a logger $\mathit{lg}$ of type $\capt{\mathit{Logger}}{\cset{\mathit{out}}}$ that writes to a file $\mathit{out}$, it gives $\cset{\mathit{lg}} \mathrel{<:} \cset{\mathit{out}}$ (\texttt{overview.md}, lines 86 to 92). The set $\cset{\mathsf{any}}$ covers every capture set (\texttt{basics.md}, line 296).

Following the third case from a variable to the capture set of its type, and on, has to end somewhere. In Scala it ends at \lstinline|any|, which the trees of this report read differently (Sections~\ref{sec:source-any} and~\ref{sec:levels}). In this report a program runs over a platform, a list of capture variables $\kappa_1, \kappa_2, \ldots$ that stand for primitive capabilities such as a file system or a console. A platform capture variable stands for itself. The capture variables that a capture set reaches by replacing variables with the capture sets of their types are the leaves of the set (Section~\ref{sec:mini-leaves}). A term variable is never a leaf, and a variable whose type has the empty capture set has no leaves. From now on, ``$C$ is covered by $D$'' means that every leaf of $C$ is a leaf of $D$, and the word subcapturing is kept for derivations. Whether every derivation yields coverage is the question of Section~\ref{sec:problem}.

\subsection{What a closure's capture set bounds}\label{sec:cc-closures}

The capture set of a closure can be read in two ways. In this report it bounds what calling the closure may use, and creating a closure uses nothing. This is the reading of System Capless \cite{xu2025box}, which types a lambda with the empty use set. In the \FCdot target of Section~\ref{sec:mini} a closure carries its capture set, called its annotation, and evidence that the use set of its body lies within the annotation and the parameter.

Scala's documentation states the other reading. ``A function captures any capabilities accessed by its body'' (\texttt{overview.md}, line 107). And a use is charged to every scope around it: ``When a capability is used, it must be checked for compatibility with the capture-set constraints of all enclosing scopes'' (\texttt{scoped-capabilities.md}, lines 126 and 127). Under this rule a closure accounts for the uses of the closures it creates, even when it only returns them.

The running example of Section~\ref{sec:mini} is where the two readings come apart. Its platform has two capture variables $\kappa_1$ and $\kappa_2$ and two capabilities, $\mathit{log}$ with capture set $\cset{\kappa_1}$ and $\mathit{console}$ with capture set $\cset{\kappa_2}$. The closure $\mathit{c1}$ calls $\mathit{log}$ and returns a closure that calls $\mathit{console}$. In this report the annotation of $\mathit{c1}$ is $\cset{\mathit{log}}$. Its result type $\capt{(\Unit \to \Unit)}{\cset{\mathit{console}}}$ records that the returned closure may use $\mathit{console}$ when it is called. By the documentation's charging rule, that use is also charged to $\mathit{c1}$, whose annotation would then be $\cset{\mathit{log}, \mathit{console}}$. We state this from the documentation and do not claim what the Scala compiler infers for $\mathit{c1}$. The program $\mathit{prog}_2$ calls $\mathit{c1}$ and drops the result. In this report its use set has the leaf $\kappa_1$ and not the leaf $\kappa_2$, and Section~\ref{sec:mini-run} proves that no state of its run inspects a variable with leaf $\kappa_2$. A declared set may be larger than the body needs (Example~\ref{ex:mini-typing}), so $\mathit{c1}$ with the charging annotation is typed here too, but for it effect safety no longer excludes $\kappa_2$. The two readings differ in where a use is paid for. Here a call pays for the closure it runs, and a closure it returns is paid for when that closure is called in turn.

\subsection{Use sets and inspection}\label{sec:cc-uses}

A use set is a capture set that bounds what a term may use when it runs. System Capless makes the use set the first index of its typing judgment, and the source calculus of this report does the same, $\dtyuj{U}{\Gamma}{t}{T}$ (Section~\ref{sec:source-calc}). A variable uses itself, a call uses the function and the argument, and a closure uses nothing until it is called.

A let needs care. In $\klet x = t \kin u$ the body $u$ may use $x$, but $x$ is not visible outside the let, so the use set of the let cannot mention it. The reference meets the same problem in types and calls its answer avoidance. A local variable in a type is replaced by the smallest visible capture set that covers it, so $\cset{l}$, for a local logger $l$ of type $\capt{\mathit{Logger}}{\cset{\mathit{fs}}}$, widens to $\cset{\mathit{fs}}$ (\texttt{basics.md}, lines 299 to 308). In the target \FCdot of this report a let declares the use set of its body, a set $U$ that does not mention $x$, and carries evidence $f$ that the uses of the body fit $U$. Section~\ref{sec:mini-typing} writes it $\letc{x}{t}{u}{U}{f}$. Every set that a binder declares is part of the term, so the use set $\uses{t}$ of a term is computed from its syntax. The source has no declared sets. The translation produces them (Section~\ref{sec:source}).

Not every use reads a stored value. A step inspects a variable when it reads the value stored there: the function of a call, whose closure it runs, the receiver of a projection, whose field it reads, and the operand of an unboxing, whose box it opens. An argument is used and not inspected. The call $x\,y$ uses $x$ and $y$ and inspects $x$ only.

\subsection{Capability members, escape, boxes and classifiers}\label{sec:cc-later}

Four more features of the checker appear later in the report, each with one paragraph here. Reach capabilities and separation checking are left out (Section~\ref{sec:related}).

\paragraph{Capability members.}
A capture set can be abstract. The reference shows a reactor whose event handlers may capture only what an abstract capability member allows (\texttt{polymorphism.md}, lines 197 to 205):
\begin{lstlisting}[language=Scala]
trait Reactor:
  type Cap^ <: {caps.any}
  def onEvent(h: Event ->{this.Cap} Unit): Unit

trait GUIReactor extends Reactor:
  type Cap^ <: {ui, log}
\end{lstlisting}
A capability member behaves like a path-dependent capture-set variable (line 192). DOT models a type parameter as a type member, and this report models a capture parameter as a capture member $\dcap{C}{C_1}{C_2}$ of an object, with bounds $C_1$ and $C_2$. Inside a capture set, $\dsel{x}{C}$ names the member $C$ of $x$. Sections~\ref{sec:target-members} and~\ref{sec:source} treat them on the Lean's example C2, which resembles the reactor: an object with a capture member bounded by two capabilities and a field whose closure captures that member.

\paragraph{Escape and scopes.}
The reference's page on scoped capabilities rejects an escape like that of Section~\ref{sec:intro}, for a method \lstinline|withFile| (\texttt{scoped-capabilities.md}, lines 417 to 419):
\begin{lstlisting}[language=Scala,basicstyle=\ttfamily\footnotesize,columns=fixed,basewidth=0.52em]
val escaped: () => File^ = withFile[() => File^]("test.txt")(f => () => f) // error
//           ^^^^^^^^^^^ any here is in the outer scope
escaped().read()  // Use-after-close!
\end{lstlisting}
The reference gives two mechanisms against escapes from \lstinline|withFile| (lines 169 to 183). First, every class, method body and block has its own local \lstinline|any|, and each capability has a level, the local \lstinline|any| of its defining scope. It can flow only into the \lstinline|any|s of its own scope or of nested ones (lines 28 to 30 and 85 to 111). This stops an escape through a mutable variable. Second, a function type may write \lstinline|fresh| in its result, which says that each call yields a new capability. Such a result is isolated and cannot be merged with capabilities of the enclosing scope (lines 40 to 44). This stops the returned closure above. To hide \lstinline|f|, its type \lstinline|() ->{f} File^{f}| would have to widen to an existentially bound \lstinline|fresh|, which cannot flow into the outer \lstinline|any| of the expected type (lines 396 to 412). Section~\ref{sec:levels} models scopes, levels and fresh results in \treeCC, treats the returned closure by levels, and says how much of that escape is proved.

\paragraph{Boxes.}
A pair of two capabilities can have a pure type. The reference types \lstinline|Pair(x, y)|, for \lstinline|x| capturing \lstinline|ct| and \lstinline|y| capturing \lstinline|fs|, at a \lstinline|Pair| type with no outer capture set, and the capture reappears when a component is accessed (\texttt{classes.md}, lines 186 to 206). This is capture tunneling. The theory explains it with boxes, and the compiler inserts box and unbox operations that have no run-time effect: ``Boxing hides a capture set and unboxing recovers it'' (\texttt{internals.md}, lines 37 to 46). The calculi of this report have boxes as terms. A box is pure, and an unboxing charges the boxed set against its use set. A step that unboxes inspects the box, which has no leaves, so effect safety never flags it. Section~\ref{sec:target-boxes} gives a separate theorem about the unboxed value. The trees refuse an \lstinline|any| under a box, in a type-member bound or in the lower bound of a capture member (Section~\ref{sec:source-any}).

\paragraph{Classifiers.}
Capabilities can be sorted by kind. \lstinline|Try.apply| runs a body that may use anything. Its result drops the capabilities of the body that are known to be unrelated to \lstinline|Control| and keeps the rest (\texttt{classifiers.md}, lines 95, 96 and 104 to 113):
\begin{lstlisting}[language=Scala]
object Try:
  def apply[T](body: => T): Try[T]^{body.only[Control]} = ???
\end{lstlisting}
A method that runs its argument on another thread admits only capabilities known to be unrelated to \lstinline|Control| (lines 128 and 135):
\begin{lstlisting}[language=Scala]
def runOnNewThread[T](body: () ->{any.except[Control]} T): T = ???
\end{lstlisting}
Section~\ref{sec:classifiers} models classifiers in \treeCL. Its examples model \lstinline|Try.apply| and, in place of \lstinline|runOnNewThread|, a \lstinline|Future.apply| whose body may capture anything except thread-local capabilities. That is the thread example of Capless(K), System Capless with classifiers \cite{pham2026classifying}.
