\section{Capture Checking for a Reader of Report~1}\label{sec:cc}
\mathplain

This section follows the Scala 3 reference \cite{scala3cc}. It fixes the words that the rest of the report uses: capability, capturing type, subcapturing, the roots of a capture set, coverage, use set and inspection. Section~\ref{sec:cc-closures} settles what the capture set of a closure bounds, which is where the report and Scala's documentation differ.

\subsection{Capabilities and capturing types}\label{sec:cc-types}

A capability is a value of interest, such as a file handle, an access token or a mutable data structure, and often it gives access to an effect. A capturing type $\capt{T}{\cset{c_1, \ldots, c_n}}$ stands for instances of $T$ that retain the capabilities $c_1$ to $c_n$, and Section~\ref{sec:cc-closures} fixes how this report reads the set. A type $T$ with no capture set, whose class does not extend \lstinline|Capability|, is pure and stands for $\capt{T}{\cempty}$ (\texttt{overview.md}, lines 78 to 80). In Scala source, a capability is a parameter, a local variable or the \lstinline|this| of a class whose type is a capturing type with a nonempty capture set (\texttt{basics.md}, lines 118 to 120).

Function types carry capture sets in the same way (\texttt{basics.md}, lines 158 to 166). The arrow \lstinline|A -> B| is pure. The arrow \lstinline|A ->{c, d} B| abbreviates \lstinline|(A -> B)^{c, d}|, a function that can capture $c$ and $d$ and no others. The impure arrow \lstinline|A => B| is \lstinline|A ->{any} B|. Here \lstinline|any| is the universal capability, from which every other capability is derived.

Capture sets are ordered by subcapturing. The reference writes $C_1 \mathrel{<:} C_2$ and reads it as ``$C_1$ is covered by $C_2$'' (\texttt{basics.md}, line 269). Subtyping extends to capturing types: $\capt{T_1}{C_1} \mathrel{<:} \capt{T_2}{C_2}$ when $T_1 \mathrel{<:} T_2$ and $C_1 \mathrel{<:} C_2$. Subcapturing $C_1 \mathrel{<:} C_2$ holds when every element $c$ of $C_1$ meets one of three conditions (lines 277 to 281):
\begin{enumerate}
\item $c$ is an element of $C_2$,
\item $c$ refers to a parameter of a class \lstinline|Cls| and $C_2$ contains \lstinline|Cls.this| (this report does not model class parameters),
\item the type of $c$ has a capture set $C$ and $C \mathrel{<:} C_2$.
\end{enumerate}
The third case says that a capability is covered by the capture set of its type. It becomes rule \rn{C-Var} of Section~\ref{sec:mini-typing}, and it makes a capture set mean more than its elements. For a logger $\mathit{lg}$ of type $\capt{\mathit{Logger}}{\cset{\mathit{out}}}$ that writes to a file $\mathit{out}$, it gives $\cset{\mathit{lg}} \mathrel{<:} \cset{\mathit{out}}$ (\texttt{overview.md}, lines 86 to 92).

Following the third case from a variable to the capture set of its type, and on, has to end somewhere. In Scala it ends at \lstinline|any|, and $\cset{\mathsf{any}}$ covers every capture set. In this report a program runs over a platform, a list of capture variables $\kappa_1, \kappa_2, \ldots$ that stand for primitive capabilities such as a file system or a console. A capture variable is bound in the context, as a type variable is in System~F. The capture variables that a capture set reaches by replacing variables with the capture sets of their types are the roots of the set (Section~\ref{sec:mini-roots}), the word that System Capybara uses \cite{xu2026capybara}. If the file $\mathit{out}$ above has the type $\capt{\mathit{File}}{\cset{\kappa_{\mathit{fs}}}}$ for a platform variable $\kappa_{\mathit{fs}}$, the roots of $\cset{\mathit{lg}}$ are those of $\cset{\mathit{out}}$, which are $\cset{\kappa_{\mathit{fs}}}$ (on paper). The roots of a variable $x$ are those of $\cset{x}$. They are not report~1's root of the atom $x$, the variable under its casts (Section~\ref{sec:recap}), nor \lstinline|any|, which the reference calls the root capability (\texttt{basics.md}, line 296).

Unlike the reference, the calculi of this report admit every term variable in a capture set, because a use set collects the variables a term mentions (Section~\ref{sec:cc-uses}). A variable whose type has the empty capture set has no roots and adds nothing to a set. A variable $x$ acts as a capability when $\cset{x}$ has a root, as $\mathit{lg}$ does.

From now on, the reference's phrase ``$C$ is covered by $D$'' means that every root of $C$ is a root of $D$, and the word subcapturing is kept for derivations. Whether every derivation yields coverage is the question of Section~\ref{sec:problem}.

\subsection{Use sets and inspection}\label{sec:cc-uses}

A use set is a capture set that bounds what a term may use when it runs. System Capless \cite{xu2025box}, a core calculus for Scala's capture checker, makes the use set the first index of its typing judgment. The source calculus of this report does the same, $\dtyuj{U}{\Gamma}{t}{T}$ (Section~\ref{sec:source-calc}). A variable uses itself, and a call uses the function and the argument.

A let needs care. In $\klet x = t \kin u$ the body $u$ may use $x$, but $x$ is not visible outside the let, so the use set of the let cannot mention it. The reference meets the same problem in types and calls its answer avoidance. A local variable in a type is replaced by the smallest visible capture set above it, so $\cset{l}$, for a local logger $l$ of type $\capt{\mathit{Logger}}{\cset{\mathit{fs}}}$, widens to $\cset{\mathit{fs}}$ (\texttt{basics.md}, lines 299 to 308). The target of this report records the answer in the term. A let declares a set without $x$ and carries evidence that the body fits it, with each use of $x$ widened to the capture set of its type (Section~\ref{sec:mini-typing}). The source has no declared sets. The translation produces them (Section~\ref{sec:source}).

Not every use reads a stored value. A step inspects a variable when it reads the value stored there. A call inspects its function and runs the closure stored there. A projection inspects its receiver and reads a field. An unboxing inspects its operand and opens the box. An argument is used and not inspected, so the call $x\,y$ uses $x$ and $y$ and inspects $x$ only.

Why does effect safety speak of inspection? The calculi of this report have no primitive effects. A platform capture variable stands for one, such as writing to a log, and a run exercises it by calling a closure whose capture set has it as a root. That call inspects the closure's variable. So the store may hold a closure whose capture set has a root that the use set lacks, as long as no step reads it (Example~\ref{ex:mini-prog2}).

\subsection{What a closure's capture set bounds}\label{sec:cc-closures}

The capture set of a closure can be read in two ways, and they differ in where a use is paid for. In this report it bounds what calling the closure may use, and creating a closure uses nothing. A closure that a call returns is paid for when it is called in turn. This is the reading of System Capless, which types a lambda with the empty use set. In the target of Section~\ref{sec:mini} a closure carries its capture set, called its annotation, and evidence that the use set of its body lies within the annotation and the parameter.

Scala's documentation states the other reading. ``A function captures any capabilities accessed by its body'' (\texttt{overview.md}, line 107). And a use is charged to every scope around it: ``When a capability is used, it must be checked for compatibility with the capture-set constraints of all enclosing scopes'' (\texttt{scoped-capabilities.md}, lines 126 and 127). Under this rule a closure pays for the closures it creates, even when it only returns them.

The running example of Section~\ref{sec:mini} is built on the closure that System Capless uses to show the difference. Its platform has two capture variables $\kappa_1$ and $\kappa_2$. Its store holds a unit value $\mathit{unit}$ and two capabilities, $\mathit{log} : \capt{(\forall(w : \Unit)\,\Unit)}{\cset{\kappa_1}}$ and $\mathit{console} : \capt{(\forall(w : \Unit)\,\Unit)}{\cset{\kappa_2}}$. The closure $\mathit{c1}$ calls $\mathit{log}$ and returns a closure that calls $\mathit{console}$, and two programs call it:
\[
\begin{array}{@{}lcl@{}}
\mathit{c1} & = & \lambda(y : \Unit).\ \klet r = \mathit{log}\,y \kin \lambda(z : \Unit).\,\mathit{console}\,z \\
\mathit{prog}_1 & = & \klet \mathit{inner} = \mathit{c1}\,\mathit{unit} \kin \mathit{inner}\,\mathit{unit} \\
\mathit{prog}_2 & = & \klet \mathit{inner} = \mathit{c1}\,\mathit{unit} \kin \mathit{unit}
\end{array}
\]
In this report $\mathit{c1}$ has the type $\capt{(\forall(y : \Unit)\,\capt{(\forall(z : \Unit)\,\Unit)}{\cset{\mathit{console}}})}{\cset{\mathit{log}}}$ (decided, Example~\ref{ex:mini-typing}). Its annotation $\cset{\mathit{log}}$ bounds what a call of $\mathit{c1}$ may use, and the inner set $\cset{\mathit{console}}$ bounds what a call of the returned closure may use. As the paper on System Capless notes \cite{xu2025box}, $\mathrm{CC}_{<:\square}$, the calculus of capturing types \cite{boruchgruszecki2023capturing}, gives $\mathit{c1}$ the set $\cset{\mathit{log}, \mathit{console}}$ instead. So $\mathit{prog}_2$, which drops the returned closure, is charged for $\mathit{console}$ by the documentation's reading and not by this report's. Section~\ref{sec:mini-run} proves that its run never calls $\mathit{console}$.

\subsection{Capability members, escape, boxes and classifiers}\label{sec:cc-later}

Four more features of the checker appear later in the report.

\paragraph{Capability members.}
A capture set can be abstract. The reference shows a reactor whose event handlers may capture only what an abstract capability member allows (\texttt{polymorphism.md}, lines 197 to 205):\par\nopagebreak
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Scala,belowskip=0pt]
trait Reactor:
  type Cap^ <: {caps.any}
  def onEvent(h: Event ->{this.Cap} Unit): Unit
\end{lstlisting}
\end{minipage}\par
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Scala]
trait GUIReactor extends Reactor:
  type Cap^ <: {ui, log}
\end{lstlisting}
\end{minipage}\par\noindent
A capability member behaves like a path-dependent capture-set variable (line 192). DOT models a type parameter as a type member, and \treeK models a capture parameter as a capture member $\dcap{C}{C_1}{C_2}$ of an object, with bounds $C_1$ and $C_2$. Inside a capture set, $\dsel{x}{C}$ names the member $C$ of $x$. In this notation \lstinline|GUIReactor| declares $\dcap{C}{\cempty}{\cset{\mathit{ui}, \mathit{log}}}$, and a handler of a reactor $r$ has type $\capt{(\forall(e : \mathit{Event})\,\Unit)}{\cset{\dsel{r}{C}}}$. Section~\ref{sec:target-members} treats capture members on the Lean's example C2, which resembles the reactor.

\paragraph{Escape and scopes.}
The reference's page on scoped capabilities rejects an escape like that of Section~\ref{sec:intro}, for a method \lstinline|withFile| (\texttt{scoped-capabilities.md}, lines 417 to 419):\par\nopagebreak
\noindent\begin{minipage}{\linewidth}
\begin{lstlisting}[language=Scala,basicstyle=\ttfamily\footnotesize,columns=fixed,basewidth=0.52em]
val escaped: () => File^ = withFile[() => File^]("test.txt")(f => () => f) // error
//           ^^^^^^^^^^^ any here is in the outer scope
escaped().read()  // Use-after-close!
\end{lstlisting}
\end{minipage}\par\noindent
The reference stops such escapes by scopes. Every class, method body and block has its own local \lstinline|any|, and a capability may flow only into the \lstinline|any| of its own scope or of a nested one. It stops the escape above by a second rule. A result marked \lstinline|fresh| is a new capability at each call and cannot be merged with the capabilities of the enclosing scope (Section~\ref{sec:levels-fresh}). \treeCC models both.

\paragraph{Boxes.}
A pair of two capabilities can have a pure type, and the capture reappears when a component is accessed (\texttt{classes.md}, lines 186 to 206). The theory explains this with boxes: ``Boxing hides a capture set and unboxing recovers it'' (\texttt{internals.md}, lines 37 to 46). The calculi of this report have boxes as terms, and an unboxing charges the boxed set against its use set.

\paragraph{Classifiers.}
Capabilities can be sorted by kind. \lstinline|Try.apply| runs a body that may use anything. Its result drops the capabilities of the body that are known to be unrelated to \lstinline|Control| and keeps the rest, written \lstinline|body.only[Control]| (\texttt{classifiers.md}, lines 95, 96 and 105 to 113):
\begin{lstlisting}[language=Scala]
object Try:
  def apply[T](body: => T): Try[T]^{body.only[Control]} = ???
\end{lstlisting}
A method \lstinline|runOnNewThread| that runs its argument on another thread admits only capabilities known to be unrelated to \lstinline|Control|, written \lstinline|any.except[Control]| (lines 128 and 135). Section~\ref{sec:classifiers} models classifiers in \treeCL. Sections~\ref{sec:levels} and~\ref{sec:classifiers} say where the theorems prove less than the reference promises.
